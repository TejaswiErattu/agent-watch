# Requirements Document

## Introduction

Agent Watch is an observability and control system for AI agents built by students. The system provides real-time monitoring of agent actions (LLM calls and tool invocations), cost tracking, guardrails enforcement, and alerting capabilities. The MVP enables students to wrap their Python agents in a lightweight SDK, stream events to a serverless API, and view/control agent behavior through a web dashboard.

Identity in the MVP is deliberately simple: an Owner is identified by an `ownerId` plus a SHA-256 hash of an API key. There are no user accounts and no login. The SDK talks only to the Ingestion_API over HTTPS; all AWS service access (DynamoDB, SNS) happens inside the Ingestion_API.

## Glossary

- **Agent_Watch_System**: The complete system comprising SDK, API, storage, and dashboard
- **SDK**: The Python client library (`agentwatch` package) that wraps agent code
- **Ingestion_API**: The HTTP API (Amazon API Gateway) and its AWS Lambda handlers that serve all Agent Watch routes: event ingestion, inventory, timeline, guardrail config, and spend
- **Event**: A structured record of an agent action (LLM call, tool call, or blocked action) with metadata
- **Agent**: A Python program using LLM APIs and tools, wrapped by the SDK
- **Owner**: The student who runs an agent, identified by the pair (`ownerId`, Key_Hash). The Owner has no user account and no password
- **ownerId**: A string chosen by the Owner that groups agents for the inventory
- **API_Key**: A secret string chosen or generated by the Owner, configured in the SDK and entered in the Dashboard. The plaintext API_Key is never transmitted to or stored by the Ingestion_API
- **Key_Hash**: The lowercase hex SHA-256 digest of the API_Key. The Key_Hash functions as a bearer credential and is sent only over HTTPS
- **Credentials**: The `ownerId` and Key_Hash sent together in request headers to the Ingestion_API
- **Key_Verifier**: The lowercase hex SHA-256 digest of the Key_Hash, computed by the Ingestion_API. The Agent_Record stores the Key_Verifier, never the Key_Hash
- **Matching_Credentials**: Credentials whose ownerId equals the Agent_Record ownerId and whose Key_Verifier (computed by the Ingestion_API from the received Key_Hash) equals the Key_Verifier stored in the Agent_Record
- **Agent_Record**: The single metadata record per `agentId` holding agentId, ownerId, Key_Verifier, Guardrail_Config, firstSeen timestamp, and lastSeen timestamp. firstSeen and lastSeen are null for an Agent_Record created by PUT /agents/{agentId}/config until the first event for that agent is stored
- **Unreported_Agent**: An agent whose Agent_Record has a null firstSeen, meaning no event for that agent has been stored yet
- **Guardrail**: A preventive rule (spend cap or path blocklist) enforced by the SDK before action execution
- **Guardrail_Config**: The per-agent set of guardrail rules: an optional Daily_Spend_Cap and a list of Blocked_Paths
- **Pricing_Table**: The per-model input and output token prices, derived from `backend/src/agentwatch_api/pricing.py` and returned to the SDK by the Ingestion_API
- **Config_Response**: The response of GET /agents/{agentId}/config, containing the Guardrail_Config and the Pricing_Table
- **Rolling_24h_Spend**: The sum of `costUsd` for all events of an agent with `ts` within the 24 hours before the request time
- **Local_Spend_Total**: The SDK's in-memory running estimate of Rolling_24h_Spend between syncs
- **Sync_Interval**: 60 seconds; the maximum age of the SDK's cached Guardrail_Config and Local_Spend_Total before the SDK refreshes them
- **Event_Store**: DynamoDB table storing agent events with partition key `agentId` and sort key `ts#eventId`, plus one Agent_Record per agent
- **Dashboard**: Next.js web application for viewing agents and configuring guardrails
- **Alert_Service**: SNS topic with an email subscription that notifies the Owner of guardrail violations
- **Cost_Estimator**: Component that calculates USD cost from token counts and model names
- **Blocked_Path**: A blocklist entry naming file system locations that agents are prohibited from accessing; either a Directory_Entry or a Name_Entry
- **Directory_Separator**: The character "/" or, on the SDK host, `os.sep` (and `os.altsep` when defined)
- **Directory_Entry**: A Blocked_Path that contains at least one Directory_Separator (e.g. "/home/me/project/secrets" or "~/.ssh")
- **Name_Entry**: A Blocked_Path that contains no Directory_Separator (e.g. ".env")
- **Normalized_Path**: The result of `os.path.realpath(os.path.expanduser(p))` evaluated on the SDK host, which resolves relative paths against the current working directory and removes "./" and ".." segments and symlinks
- **Absolute_Path**: The result of `os.path.normpath(os.path.abspath(os.path.expanduser(p)))` evaluated on the SDK host, which resolves relative paths against the current working directory and removes "./" and ".." segments lexically, without resolving symlinks
- **Path_Forms**: The two forms of a path p used for blocklist matching: the Absolute_Path of p and the Normalized_Path of p
- **Case_Fold**: The result of Python `str.casefold()` applied to a string; blocklist comparisons compare the Case_Fold of both sides
- **Daily_Spend_Cap**: Maximum USD amount an agent can spend in a rolling 24-hour period
- **Violation_Type**: The reason an action was blocked, with value "spend_cap" or "blocked_path"

## Requirements

### Requirement 1: SDK Event Capture

**User Story:** As a student building an agent, I want to wrap my agent code in 3 lines, so that all LLM and tool calls are automatically captured without modifying my agent logic.

#### Acceptance Criteria

1. WHEN the SDK wraps an agent, THE SDK SHALL capture every LLM API call with timestamp, model name, input tokens, output tokens, and prompt metadata
2. WHEN the SDK wraps an agent, THE SDK SHALL capture every tool invocation with timestamp, tool name, target, and arguments
3. THE SDK SHALL generate a unique `eventId` for each captured action
4. THE SDK SHALL associate each event with the configured `agentId` and `ownerId`
5. THE SDK SHALL require no more than 3 lines of code to integrate into existing agent code

### Requirement 2: Event Transmission

**User Story:** As a student running an agent, I want events sent to the API automatically, so that I can see agent activity in real time without manual logging.

#### Acceptance Criteria

1. WHEN an event is captured, THE SDK SHALL transmit the event to the Ingestion_API within 5 seconds
2. IF the Ingestion_API is unreachable, THEN THE SDK SHALL retry transmission up to 3 times with exponential backoff
3. IF all retries fail, THEN THE SDK SHALL log the failure locally and continue agent execution
4. THE SDK SHALL use HTTP POST with JSON payload to `/events` to transmit events
5. THE SDK SHALL include the Credentials (`ownerId` and Key_Hash) in the request headers of every request to the Ingestion_API
6. IF the Ingestion_API responds with HTTP 401 or 403, THEN THE SDK SHALL log an authorization error without retrying and continue agent execution

### Requirement 3: Cost Estimation

**User Story:** As a student monitoring my agent, I want to see the USD cost of each LLM call, so that I can track my spending against my personal budget.

#### Acceptance Criteria

1. WHEN an LLM event is received, THE Cost_Estimator SHALL calculate USD cost from input tokens, output tokens, and model name
2. THE Cost_Estimator SHALL support pricing for Claude models on Amazon Bedrock
3. THE Cost_Estimator SHALL support pricing for Claude models via Anthropic API
4. THE Cost_Estimator SHALL return a cost of 0.0 USD for unknown models
5. THE Cost_Estimator SHALL store all pricing data in `backend/src/agentwatch_api/pricing.py`
6. FOR ALL valid events with known models, calculating cost then formatting then parsing SHALL produce an equivalent cost value within 0.0001 USD (round-trip property)
7. THE Ingestion_API SHALL generate the Pricing_Table in every Config_Response from `backend/src/agentwatch_api/pricing.py`
8. THE SDK SHALL obtain all model prices from the Pricing_Table in the most recent Config_Response, with no prices hardcoded in the SDK source
9. FOR ALL models and token counts, THE SDK cost computed from the Pricing_Table SHALL equal the Cost_Estimator cost within 0.0001 USD (model-based property)
10. WHEN the SDK computes a cost for a model not present in the Pricing_Table of a successfully fetched Config_Response, THE SDK SHALL use a cost of 0.0 USD and log a warning naming the model, at most once per model per process
11. THE Cost_Estimator pricing data SHALL include the exact model IDs used by `demo/demo_agent.py` and `demo/bad_agent.py`, including the Amazon Bedrock cross-region inference-profile IDs (`us.anthropic.*`) and the Anthropic API model ID used by the fallback

### Requirement 4: Event Storage

**User Story:** As the system, I want to store events durably, so that students can review historical agent activity and spending.

#### Acceptance Criteria

1. WHEN the Ingestion_API receives an authorized and valid event, THE Ingestion_API SHALL store the event in the Event_Store within 1 second
2. THE Event_Store SHALL use `agentId` as the partition key
3. THE Event_Store SHALL use `ts#eventId` as the sort key to enable chronological ordering
4. THE Event_Store SHALL maintain a Global Secondary Index on `ownerId` for multi-agent queries
5. THE Event_Store SHALL store events with attributes: agentId, ownerId, ts, eventId, type, tool, target, inputTokens, outputTokens, costUsd, meta, and for blocked events violationType and attemptedCostUsd or attemptedPath
6. THE Ingestion_API SHALL store event items without the Key_Hash or Key_Verifier attribute
7. THE Event_Store SHALL hold exactly one Agent_Record per `agentId`, containing agentId, ownerId, Key_Verifier, Guardrail_Config, firstSeen, and lastSeen
8. WHEN the Ingestion_API receives an authorized and valid event with the same agentId, ts, and eventId as an already stored event, THE Ingestion_API SHALL return HTTP 200 marked as a duplicate, without storing a second copy, without adding the event's cost to the agent's total spend again, and without publishing an alert

### Requirement 5: Agent Inventory

**User Story:** As a student with multiple agents, I want to see a list of all my agents, so that I can quickly navigate to the one I want to monitor.

#### Acceptance Criteria

1. WHEN the Dashboard requests the inventory with Credentials, THE Ingestion_API SHALL return all agents whose Agent_Record matches the Credentials as Matching_Credentials, including Unreported_Agents
2. FOR ALL agents in the inventory, THE Ingestion_API SHALL include agentId, owner, model, first seen timestamp, last seen timestamp, and total spend
3. THE Ingestion_API SHALL calculate total spend by summing costUsd for all events with matching agentId
4. THE Ingestion_API SHALL return inventory results within 2 seconds
5. WHEN no Agent_Record matches the Credentials, THE Ingestion_API SHALL return HTTP 200 with an empty agent list
6. THE Ingestion_API SHALL take first seen and last seen timestamps from the Agent_Record
7. FOR ALL Unreported_Agents in the inventory, THE Ingestion_API SHALL return null first seen timestamp, null last seen timestamp, null model, and a total spend of 0.0 USD

### Requirement 6: Agent Timeline

**User Story:** As a student debugging my agent, I want to see a chronological feed of all actions my agent took, so that I can identify where it went wrong.

#### Acceptance Criteria

1. WHEN the Dashboard requests a timeline for an agent with authorized Credentials, THE Ingestion_API SHALL return all events for that agentId in chronological order
2. THE Ingestion_API SHALL return timeline results within 2 seconds
3. FOR ALL events in the timeline, THE Ingestion_API SHALL include timestamp, type, tool or model name, target, token counts, and cost
4. THE Timeline SHALL display LLM calls and tool calls in a unified ordered list

### Requirement 7: Spend Cap Guardrail

**User Story:** As a student on a tight budget, I want to set a daily spending limit for my agent, so that a runaway loop cannot drain my entire API credit.

#### Acceptance Criteria

1. WHEN the cached Guardrail_Config (Requirement 21) contains a Daily_Spend_Cap, THE SDK SHALL enforce the cap before executing any LLM call
2. WHEN the SDK initializes, THE SDK SHALL request the Rolling_24h_Spend from GET /agents/{agentId}/spend (Requirement 24) and set the Local_Spend_Total to the returned value
3. WHEN an LLM call completes, THE SDK SHALL add the cost of that call, computed from the Pricing_Table and the call's actual token counts, to the Local_Spend_Total
4. WHEN the SDK checks the spend cap and the Local_Spend_Total was last synced more than one Sync_Interval earlier, THE SDK SHALL request the Rolling_24h_Spend and replace the Local_Spend_Total with the returned value before evaluating the cap
5. THE SDK SHALL estimate the cost of a pending LLM call from the Pricing_Table, the model name, an input token estimate derived from the request content, and the request's maximum output tokens
6. IF the Local_Spend_Total plus the estimated cost of the pending call exceeds the cap, THEN THE SDK SHALL block the call, report the block as specified in Requirement 10, and raise an exception
7. IF the Local_Spend_Total plus the estimated cost of the pending call is less than or equal to the cap, THEN THE SDK SHALL allow the call to proceed
8. THE SDK SHALL check the spend cap before every LLM API call
9. IF a Rolling_24h_Spend request fails or exceeds a 2-second timeout, THEN THE SDK SHALL keep the current Local_Spend_Total, log a warning, and continue the spend check
10. IF no Rolling_24h_Spend request has ever succeeded, THEN THE SDK SHALL use a Local_Spend_Total starting at 0.0 USD plus the costs of LLM calls completed since initialization

### Requirement 8: Path Blocklist Guardrail

**User Story:** As a student with sensitive files in my project, I want to block my agent from accessing specific paths, so that it cannot accidentally read my API keys or credentials.

#### Acceptance Criteria

1. WHEN the cached Guardrail_Config (Requirement 21) contains one or more Blocked_Paths, THE SDK SHALL enforce the blocklist before executing any tool call that accesses file paths
2. WHEN a tool call attempts to access a path that matches a Blocked_Path under criteria 4 through 6, THE SDK SHALL block the call, report the block as specified in Requirement 10, and raise an exception
3. WHEN a tool call attempts to access a path that matches no Blocked_Path under criteria 4 through 6, THE SDK SHALL allow the call to proceed
4. WHEN the SDK checks a tool call against the blocklist, THE SDK SHALL compute the Path_Forms of the attempted path before matching and SHALL treat the attempted path as matching a Blocked_Path if either of its Path_Forms matches that Blocked_Path under criteria 5 and 6
5. WHEN the SDK matches against a Directory_Entry, THE SDK SHALL compute the Path_Forms of the Directory_Entry and treat an attempted Path_Form as matching if its Case_Fold equals the Case_Fold of either entry Path_Form or begins with the Case_Fold of either entry Path_Form followed by a Directory_Separator (blocking "/a/b" blocks "/a/b", "/A/B", and "/a/b/c", but not "/a/bc")
6. WHEN the SDK matches against a Name_Entry, THE SDK SHALL treat an attempted Path_Form as matching if the Case_Fold of its final component (file name) equals the Case_Fold of the Name_Entry, in any directory (".env" blocks ".env" and ".ENV")
7. THE SDK SHALL check the path blocklist before every file access tool call
8. WHEN the SDK checks the path blocklist and the cached Guardrail_Config was fetched more than one Sync_Interval earlier, THE SDK SHALL refresh the Guardrail_Config as specified in Requirement 21 before evaluating the blocklist
9. FOR ALL attempted paths p and Guardrail_Configs, THE SDK block decision for p SHALL equal the block decision for p with a "./" prefix and for p with an inserted "dir/../" segment where dir is an existing non-symlink directory; and FOR ALL attempted paths p that contain no symlink components and are blocked, THE SDK SHALL also block any symlink that resolves to the same file as p, so a symlink alias may add blocks but never remove them (metamorphic property)
10. FOR ALL Directory_Entries e and attempted paths formed by appending one or more non-separator characters directly to the Normalized_Path of e (e.g. "/a/b" and "/a/bc"), where neither e nor the attempted path involves a symlink, THE SDK SHALL allow the call when the Guardrail_Config contains e as the only Blocked_Path (property)
11. WHEN the attempted path is a symlink whose own file name matches a Name_Entry under criterion 6 (e.g. ".env" pointing to "secrets.txt"), THE SDK SHALL block the call
12. FOR ALL attempted paths and Blocked_Paths that involve no symlinks, THE SDK block decision SHALL be unchanged when the case of any characters in the attempted path or in any Blocked_Path is changed (case-invariance property)

### Requirement 9: Guardrail Configuration

**User Story:** As a student managing my agents, I want to configure spend caps and blocked paths through the Dashboard, so that I can adjust guardrails without editing code.

#### Acceptance Criteria

1. THE Dashboard SHALL provide a rules editor interface for each agent
2. WHEN the rules editor loads, THE Dashboard SHALL request GET /agents/{agentId}/config and display the returned Guardrail_Config
3. WHEN the Owner saves a daily spend cap in USD, THE Dashboard SHALL send PUT /agents/{agentId}/config with the full updated Guardrail_Config
4. WHEN the Owner adds a blocked path, THE Dashboard SHALL send PUT /agents/{agentId}/config with the full updated Guardrail_Config including the new path
5. WHEN the Owner removes a blocked path, THE Dashboard SHALL send PUT /agents/{agentId}/config with the full updated Guardrail_Config excluding the removed path
6. WHEN a PUT /agents/{agentId}/config request succeeds, THE Dashboard SHALL display the Guardrail_Config returned in the response
7. IF a PUT /agents/{agentId}/config request fails, THEN THE Dashboard SHALL display an error message and keep the Owner's unsaved edits in the rules editor

### Requirement 10: Guardrail Alerts

**User Story:** As a student running a long-running agent, I want to receive an email when my agent violates a guardrail, so that I can take action even when I'm not watching the Dashboard.

#### Acceptance Criteria

1. WHEN the SDK blocks an action due to a spend cap violation, THE SDK SHALL POST an event with type "blocked", violationType "spend_cap", and attemptedCostUsd set to the estimated cost of the blocked call to the Ingestion_API at `/events`
2. WHEN the SDK blocks an action due to a blocked path violation, THE SDK SHALL POST an event with type "blocked", violationType "blocked_path", and attemptedPath set to the path the tool call attempted to access to the Ingestion_API at `/events`
3. WHEN the Ingestion_API stores a valid blocked event, THE Ingestion_API SHALL publish an alert message to the Alert_Service SNS topic
4. WHEN a blocked event reaches the Ingestion_API, THE Alert_Service SHALL deliver the alert email to the subscribed Owner email address within 10 seconds, measured from the time the Ingestion_API receives the event
5. THE Alert_Service email SHALL include agentId, violation type, timestamp, and relevant details (attempted cost or attempted path)
6. THE Alert_Service SHALL use Amazon SNS for email delivery
7. THE SDK SHALL communicate with the Agent_Watch_System exclusively through HTTPS requests to the Ingestion_API, with no direct calls to AWS services (no boto3, SNS, or DynamoDB access from the SDK)
8. IF publishing to the Alert_Service fails, THEN THE Ingestion_API SHALL keep the stored blocked event, log the publish failure, and return a success response to the SDK

### Requirement 11: Dashboard Inventory Page

**User Story:** As a student, I want to view my agent inventory on a web page, so that I can see all my agents and their status at a glance.

#### Acceptance Criteria

1. THE Dashboard SHALL display an inventory page listing all agents for the Owner identified by the Credentials stored in the Dashboard
2. FOR ALL agents, THE Dashboard SHALL display agentId, model, last activity timestamp, and total spend
3. WHEN I click on an agent, THE Dashboard SHALL navigate to that agent's detail page
4. THE Dashboard SHALL refresh the inventory data every 30 seconds while the page is open
5. WHILE no Credentials are stored in the browser, THE Dashboard SHALL display a form requesting the ownerId and API_Key
6. WHEN the Owner submits the credentials form, THE Dashboard SHALL compute the Key_Hash in the browser, store the ownerId and Key_Hash in browser local storage, and discard the plaintext API_Key
7. THE Dashboard SHALL include the stored Credentials in the request headers of every request to the Ingestion_API
8. IF the Ingestion_API responds with HTTP 401 or 403, THEN THE Dashboard SHALL display an authorization error and the credentials form
9. WHEN the Owner selects the clear credentials control, THE Dashboard SHALL remove the stored Credentials from browser local storage
10. FOR ALL Unreported_Agents in the inventory, THE Dashboard SHALL display the label "not yet reported" in place of the last activity timestamp and display no model
11. THE Dashboard SHALL provide an "add agent" control on the inventory page in which the Owner enters an agentId
12. WHEN the Owner submits an agentId in the "add agent" control, THE Dashboard SHALL open the rules editor for that agentId, including an agentId that has no Agent_Record

### Requirement 12: Dashboard Agent Detail Page

**User Story:** As a student investigating my agent's behavior, I want to view a detailed page for one agent, so that I can see its timeline and configure its guardrails.

#### Acceptance Criteria

1. THE Dashboard SHALL display an agent detail page showing the timeline and rules editor
2. THE Dashboard SHALL load timeline events in reverse chronological order with infinite scroll
3. THE Dashboard SHALL display the rules editor with current spend cap and blocked paths
4. THE Dashboard SHALL allow inline editing of guardrail rules on the detail page

### Requirement 13: Event Schema Validation

**User Story:** As the system, I want to validate event structure before storage, so that corrupt data does not break queries or calculations.

#### Acceptance Criteria

1. WHEN the Ingestion_API receives an event, THE Ingestion_API SHALL validate that required fields are present: agentId, ownerId, ts, eventId, type
2. IF type is "llm_call", THEN THE Ingestion_API SHALL validate that inputTokens, outputTokens, and model are present
3. IF type is "tool_call", THEN THE Ingestion_API SHALL validate that tool and target are present
4. IF validation fails, THEN THE Ingestion_API SHALL return HTTP 400 with a descriptive error message
5. IF validation succeeds, THEN THE Ingestion_API SHALL proceed with cost estimation and storage
6. IF type is "blocked", THEN THE Ingestion_API SHALL validate that violationType is present with value "spend_cap" or "blocked_path"
7. IF type is "blocked" and violationType is "spend_cap", THEN THE Ingestion_API SHALL validate that attemptedCostUsd is present as a non-negative number
8. IF type is "blocked" and violationType is "blocked_path", THEN THE Ingestion_API SHALL validate that attemptedPath is present as a non-empty string
9. WHEN the Ingestion_API stores a blocked event, THE Cost_Estimator SHALL record a costUsd of 0.0 for that event, since the blocked action did not run
10. IF the ownerId in the event body differs from the ownerId in the Credentials, THEN THE Ingestion_API SHALL return HTTP 400 with a descriptive error message

### Requirement 14: API Key Security

**User Story:** As a student concerned about security, I want my API key hashed before storage, so that even if the database is compromised my key cannot be stolen.

Note: the Key_Hash is a bearer credential. Anyone holding it can act as the Owner for that ownerId. This is accepted for the MVP; transport is HTTPS only. The Event_Store holds only Key_Verifiers, so a database read exposes only Key_Verifiers, which cannot be presented as Credentials.

#### Acceptance Criteria

1. WHEN the SDK is initialized with an API_Key, THE SDK SHALL compute the Key_Hash using SHA-256
2. THE SDK SHALL transmit only the Key_Hash in API requests, never the plaintext API_Key
3. THE Ingestion_API SHALL store the Key_Verifier once per agent in the Agent_Record and in no other item
4. THE SDK SHALL never log the plaintext API_Key
5. THE Ingestion_API SHALL exclude the Key_Hash and the Key_Verifier from all API responses and log output
6. THE Ingestion_API SHALL accept requests only over HTTPS
7. THE Dashboard SHALL store only the Key_Hash in browser storage, never the plaintext API_Key
8. WHEN the Ingestion_API checks Credentials against an Agent_Record, THE Ingestion_API SHALL compute the Key_Verifier as the SHA-256 digest of the received Key_Hash and compare the computed Key_Verifier with the stored Key_Verifier
9. THE Ingestion_API SHALL compare the computed Key_Verifier with the stored Key_Verifier using a constant-time comparison (e.g. `hmac.compare_digest`)
10. THE Ingestion_API SHALL never store or log the received Key_Hash

### Requirement 15: Infrastructure as Code

**User Story:** As a student deploying the system, I want all infrastructure defined in SAM templates, so that I can deploy the entire backend with one command.

#### Acceptance Criteria

1. THE Agent_Watch_System SHALL define all AWS resources in `backend/template.yaml`
2. THE template SHALL define the Ingestion_API handlers as AWS Lambda functions with Python 3.11 runtime
3. THE template SHALL define the Event_Store as a DynamoDB table with on-demand billing
4. THE template SHALL define the Alert_Service as an SNS topic with email subscription
5. THE template SHALL define an HTTP API Gateway with the routes POST /events, GET /agents, GET /agents/{agentId}/events, GET /agents/{agentId}/config, PUT /agents/{agentId}/config, and GET /agents/{agentId}/spend, each routed to an Ingestion_API handler
6. THE template SHALL deploy all resources to us-west-2 region
7. THE template SHALL grant the Ingestion_API handlers publish permission on the Alert_Service topic and read/write permission on the Event_Store, with no other AWS permissions
8. THE template SHALL configure CORS on the HTTP API to allow the Dashboard origin to call the GET and PUT routes with the Credentials headers

### Requirement 16: Demo Agent

**User Story:** As a presenter demoing Agent Watch, I want a working demo agent that triggers guardrails, so that I can show the system in action live.

#### Acceptance Criteria

1. THE Agent_Watch_System SHALL include `demo/demo_agent.py` as a well-behaved agent example
2. THE Agent_Watch_System SHALL include `demo/bad_agent.py` that attempts to read `.env` files
3. WHEN bad_agent.py runs with `.env` in the blocked paths, THE SDK SHALL block the read attempt
4. WHEN bad_agent.py is blocked, THE Alert_Service SHALL send an email alert within 10 seconds
5. THE demo agents SHALL use Amazon Bedrock with Claude as the primary LLM, falling back to Anthropic API if Bedrock is unavailable
6. THE demo agents SHALL take their Bedrock and Anthropic API model IDs from constants defined in one demo module, and a unit test SHALL check that each constant is a key in the backend Pricing_Table

### Requirement 17: Testing Coverage

**User Story:** As a developer maintaining the system, I want automated tests for core logic, so that I can refactor confidently without breaking functionality.

#### Acceptance Criteria

1. THE SDK SHALL have pytest unit tests for event capture, guardrail enforcement, config caching and fallback, Local_Spend_Total tracking, and API transmission
2. THE Ingestion_API SHALL have pytest unit tests for cost estimation, event validation, storage logic, agent registration, request authorization, config endpoints, and the spend endpoint
3. THE Dashboard SHALL have vitest unit tests for timeline rendering and rules editor
4. THE Cost_Estimator SHALL have a property-based test that verifies cost calculations are non-negative for all valid inputs
5. ALL tests SHALL run without requiring AWS credentials or live services

### Requirement 18: Free Tier Compliance

**User Story:** As a student with no budget, I want the system to stay within AWS free tier limits, so that I incur no hosting costs during development.

#### Acceptance Criteria

1. THE Event_Store SHALL use DynamoDB on-demand billing mode to minimize costs for low usage
2. THE Ingestion_API SHALL use Lambda with ARM architecture for cost efficiency
3. THE Dashboard SHALL deploy on AWS Amplify Hosting within free tier limits
4. THE Alert_Service SHALL use SNS with email protocol, staying under 1000 emails per month
5. THE Agent_Watch_System SHALL include a billing alarm set at 10 USD to alert if costs are incurred

### Requirement 19: Zero Heavy Dependencies

**User Story:** As a student integrating the SDK into my agent, I want minimal dependencies, so that installation is fast and conflicts are rare.

#### Acceptance Criteria

1. THE SDK SHALL depend only on the Python standard library and the `requests` package
2. THE SDK SHALL not require numpy, pandas, torch, boto3, or any ML framework
3. THE SDK pyproject.toml SHALL list all dependencies explicitly with version constraints
4. THE SDK SHALL install in under 10 seconds on a typical student laptop

### Requirement 20: Event Type Discrimination

**User Story:** As a student analyzing my agent, I want to filter timeline events by type, so that I can focus on LLM calls or tool calls independently.

#### Acceptance Criteria

1. THE Event SHALL include a `type` field with value "llm_call", "tool_call", or "blocked"
2. WHEN an LLM API is invoked, THE SDK SHALL create an event with type "llm_call"
3. WHEN a tool is invoked, THE SDK SHALL create an event with type "tool_call"
4. WHEN a guardrail blocks an action, THE SDK SHALL create an event with type "blocked"
5. THE Dashboard SHALL allow filtering timeline events by type

### Requirement 21: SDK Guardrail Config Sync

**User Story:** As a student, I want my agent to pick up guardrail changes I make in the Dashboard, so that a new rule takes effect without restarting the agent.

#### Acceptance Criteria

1. WHEN the SDK initializes, THE SDK SHALL request GET /agents/{agentId}/config and cache the returned Guardrail_Config and Pricing_Table in memory
2. WHEN the SDK evaluates a guardrail and the cached Config_Response was fetched more than one Sync_Interval earlier, THE SDK SHALL request GET /agents/{agentId}/config and replace the cache with the returned Config_Response
3. IF a config request fails, times out after 2 seconds, or returns a non-2xx status, THEN THE SDK SHALL keep using the last successfully fetched Config_Response and log a warning
4. IF no config request has ever succeeded, THEN THE SDK SHALL apply no Daily_Spend_Cap and no Blocked_Paths and SHALL estimate the cost of every call as 0.0 USD
5. WHILE a config refresh is failing, THE SDK SHALL retry the config request at most once per Sync_Interval
6. FOR ALL valid Guardrail_Config objects, serializing to JSON then parsing SHALL produce an equivalent Guardrail_Config (round-trip property)

### Requirement 22: Guardrail Config Endpoints

**User Story:** As a student, I want one API that stores my agent's guardrail rules, so that the Dashboard and the SDK always see the same configuration.

#### Acceptance Criteria

1. WHEN the Ingestion_API receives an authorized GET /agents/{agentId}/config, THE Ingestion_API SHALL return HTTP 200 with a Config_Response containing the Guardrail_Config from the Agent_Record and the Pricing_Table
2. WHEN the Ingestion_API receives GET /agents/{agentId}/config for an agentId with no Agent_Record, THE Ingestion_API SHALL return HTTP 200 with an empty Guardrail_Config (no Daily_Spend_Cap, no Blocked_Paths) and the Pricing_Table, without creating an Agent_Record
3. WHEN the Ingestion_API receives an authorized PUT /agents/{agentId}/config with a valid Guardrail_Config, THE Ingestion_API SHALL replace the Guardrail_Config in the Agent_Record and return HTTP 200 with the stored Guardrail_Config
4. IF a PUT /agents/{agentId}/config body has a Daily_Spend_Cap that is not a non-negative number, or Blocked_Paths that is not a list of non-empty strings, THEN THE Ingestion_API SHALL return HTTP 400 with a descriptive error message
5. WHEN an authorized PUT /agents/{agentId}/config with a valid Guardrail_Config targets an agentId with no Agent_Record, THE Ingestion_API SHALL create the Agent_Record with the ownerId from the Credentials, the Key_Verifier computed from the Credentials, the submitted Guardrail_Config, and null firstSeen and lastSeen, then return HTTP 200 with the stored Guardrail_Config
6. FOR ALL valid Guardrail_Config objects, a PUT followed by a GET for the same agentId SHALL return an equivalent Guardrail_Config (round-trip property)

### Requirement 23: Agent Registration

**User Story:** As a student, I want my agent to register itself the first time it reports in, so that I do not need a separate sign-up step.

#### Acceptance Criteria

1. WHEN the Ingestion_API receives an event for an agentId with no Agent_Record, THE Ingestion_API SHALL create an Agent_Record with the ownerId from the Credentials, the Key_Verifier computed from the Credentials, an empty Guardrail_Config, and firstSeen and lastSeen set to the event ts
2. WHEN the Ingestion_API stores the first event for an Unreported_Agent whose Agent_Record matches the Credentials as Matching_Credentials, THE Ingestion_API SHALL set firstSeen and lastSeen to the event ts and keep the stored Guardrail_Config
3. WHEN the Ingestion_API stores an event for an existing Agent_Record with a non-null lastSeen that matches the Credentials as Matching_Credentials, THE Ingestion_API SHALL update lastSeen to the later of the stored lastSeen and the event ts
4. IF the Ingestion_API receives an event for an existing Agent_Record that does not match the Credentials as Matching_Credentials, THEN THE Ingestion_API SHALL return HTTP 403 and store nothing
5. IF a PUT /agents/{agentId}/config and a first event, or two first events, for the same agentId arrive concurrently, THEN THE Ingestion_API SHALL create exactly one Agent_Record and SHALL process each request that did not create the Agent_Record against the created Agent_Record (criteria 2 through 4 for events, Requirement 22.3 and Requirement 25.2 for the PUT)

### Requirement 24: Rolling 24h Spend Endpoint

**User Story:** As a student, I want my agent to know how much it has spent in the last day, so that the spend cap works across restarts and multiple processes.

#### Acceptance Criteria

1. WHEN the Ingestion_API receives an authorized GET /agents/{agentId}/spend, THE Ingestion_API SHALL return HTTP 200 with the Rolling_24h_Spend in USD and the server timestamp used as the window end
2. WHEN the Ingestion_API receives GET /agents/{agentId}/spend for an agentId with no Agent_Record, THE Ingestion_API SHALL return HTTP 200 with a Rolling_24h_Spend of 0.0 USD
3. THE Ingestion_API SHALL return spend results within 2 seconds
4. FOR ALL sets of stored events, THE Rolling_24h_Spend SHALL equal the sum of costUsd of the events with ts in the 24 hours before the window end, and SHALL be less than or equal to the agent's total spend (metamorphic property)

### Requirement 25: Request Authorization

**User Story:** As a student, I want only someone holding my API key to read or change my agents, so that another student cannot see my data or loosen my guardrails.

#### Acceptance Criteria

1. IF a request to any Ingestion_API route lacks the ownerId or Key_Hash header, THEN THE Ingestion_API SHALL return HTTP 401
2. IF a request to an /agents/{agentId}/... route targets an existing Agent_Record that does not match the Credentials as Matching_Credentials, THEN THE Ingestion_API SHALL return HTTP 403 and return no agent data
3. WHEN a request carries Credentials that are Matching_Credentials for the targeted Agent_Record, THE Ingestion_API SHALL process the request
4. WHEN the Ingestion_API returns HTTP 401 or 403, THE Ingestion_API SHALL return a generic error body containing no ownerId, Key_Hash, Key_Verifier, or agent data

### Requirement 26: Known Limitations Documentation

**User Story:** As a student relying on guardrails, I want the README to state what the guardrails do not cover, so that I do not assume protection I do not have.

#### Acceptance Criteria

1. THE Agent_Watch_System SHALL include a "Known limitations" section in `README.md`
2. THE "Known limitations" section SHALL state that the path blocklist covers only wrapped tools that receive the path in a recognized path argument, and does not cover shell commands run by tools, direct `open()` calls in agent code, or tools whose path is not in a recognized argument
3. THE "Known limitations" section SHALL state that the Local_Spend_Total can briefly under-count during a spend sync while completed LLM call events are still queued for transmission
